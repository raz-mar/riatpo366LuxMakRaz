# Лабораторная работа 2

**Документ пользовательских требований: диаграмма прецедентов, сценарии использования, user stories и формальная проверка пользовательских требований**

Продолжение кейса лабораторной работы 1. Из дерева функций документа концепции собирается проверяемый набор пользовательских требований уровня эпика. Каждое требование оформляется пользовательской историей и сценарием использования, дерево переводится в диаграмму вариантов использования. По сценариям выделяются сущности и рисуется логическая схема данных. Затем набор проходит пошаговую проверку.

> [!NOTE]
> Новый кейс не выбирается. Берётся тот же вариант и тот же `case_concept.md`. Итог работы — файл `Документ пользовательских требований.md` рядом с документом концепции. Заготовка: [`templates/Документ пользовательских требований.md`](templates/Документ%20пользовательских%20требований.md). Полный пример на заказе справки: [`example/Документ пользовательских требований.md`](example/Документ%20пользовательских%20требований.md).

Тема 4. Часы в учебном плане не заданы.

## Что необходимо

- Готовый документ концепции лабораторной работы 1 с деревом функций.
- Редактор Markdown и Git — тот же репозиторий, в котором лежит `case_concept.md`.
- Диаграмма прецедентов — исходник PlantUML `diagrams/usecase.puml`. Логическая схема данных — исходник `diagrams/logical-data.puml`. В документ вставляется тот же код блоком `plantuml` или ссылка на файл. Картинка без `.puml` не принимается.

## Цель работы

Проверить, что каждая пользовательская цель кейса видна в дереве функций, и зафиксировать её так, чтобы заказчик, разработчик и тестировщик читали одну и ту же формулировку: эпик, история и сценарий не расходятся между собой.

Пользовательское требование в этой работе — эпик. Эпик описывает законченную цель актора, а не отдельное поле формы и не одну кнопку. У каждого эпика две записи об одном и том же требовании:

- пользовательская история: роль, действие, ценность;
- сценарий использования: кто начинает, при каком условии, какой основной поток, какие альтернативы и исключения, чем сценарий заканчивается.

## Вариант

Команда продолжает вариант лабораторной работы 1. Материалы заказчика остаются в папке этого варианта. Новый документ кладётся туда же, рядом с `case_concept.md`.

В проверку входят функции, которые в лабораторной работе 1 отнесены к рамкам кейса. Функция за рамками в эпик не превращается: в таблице реинжиниринга у неё стоит пометка «вынесен за рамки» и ссылка на раздел границ документа концепции.

## Описание задания

### 1. Реинжиниринг дерева функций

Взять дерево функций из `case_concept.md` и сверить его с пользовательскими целями кейса.

- Каждая пользовательская цель, уже заявленная в концепции как функция, пользовательская история или сценарий, получает эпик `EP-n`.
- Для каждого эпика указан узел дерева, который его покрывает.
- Если цель есть, а узла нет, узел добавляется в дерево. Если узел есть, а пользовательской цели нет, либо пишется недостающий эпик, либо узел явно выносится за рамки.
- После сверки в документ помещаются оба дерева: исходное и скорректированное. По скорректированному дереву дальше строится диаграмма. Расхождение дерева и диаграммы без пояснения не принимается.

### 2. Диаграмма вариантов использования

Скорректированное дерево переводится в UML-диаграмму вариантов использования.

- Граница системы названа по кейсу.
- Акторы — роли из профилей заинтересованных лиц лабораторной работы 1, а не «пользователь» без роли.
- Вариант использования соответствует эпику. Имя — цель актора, глаголом и объектом.
- Связи `include` и `extend` ставятся только там, где это уже видно в сценарии. Пустые стрелки «для красоты» не рисуются.
- Исходник диаграммы — `diagrams/usecase.puml`. Рендер png допустим рядом, оценивается код.

### 3. Оформление каждого эпика

Для каждого `EP-n` в документе подряд идут:

1. Идентификатор, название, узел дерева, бизнес-цель из документа концепции, источник, приоритет MoSCoW.
2. Пользовательская история в форме «Как &lt;роль&gt;, я хочу &lt;действие&gt;, чтобы &lt;ценность&gt;».
3. Сценарий использования с тем же смыслом: акторы, предусловия, триггер, основной поток, альтернативы, исключения, постусловия успеха и отказа.

История и сценарий описывают один эпик. Если в истории «чтобы успевать», а в сценарии другая цель, требование считается несогласованным.

### 4. Анализ сущностей и логическая схема данных

По сценариям эпиков выделить сущности предметной области. Схема логическая: сущности, атрибуты, которые пользователь называет, и связи с кратностью. Таблиц базы, типов полей и индексов на ней нет.

- Существительное из сценария попадает в одну из четырёх групп: сущность, которую система хранит; внешняя сущность, которую система только читает; атрибут уже названной сущности; не данные (актор, действие, правило, объект вне рамок).
- У каждой сущности указан эпик или шаг сценария, из которого она взята. Сущность без сценария не рисуется.
- Ключ — то, по чему пользователь отличает один экземпляр от другого, а не технический идентификатор реализации.
- Кратность связи следует из постусловия. «Много ко многим на всякий случай» не ставится.
- Внешняя сущность на схеме помечена и в тексте отделена от хранимых: второй копии чужого реестра система не заводит, если этого нет в границах концепции.
- Исходник — `diagrams/logical-data.puml`. Имена на схеме те же, что в таблице сущностей.

Функциональные точки по этой схеме не считаются: группы данных для точек считает лабораторная работа 3. Схема задаёт, какие сущности вообще есть.

### 5. Проверка по алгоритму

Таблицы ниже — образец приёма. В документ попадают строки вашего кейса, не строки образца.

#### Шаг 1. Подготовка к проверке

Собрать все эпики в одном разделе документа. Назначить участников: аналитик, заказчик, разработчик, тестировщик. В учебной сдаче заказчика может представлять преподаватель, остальные роли — участники команды, и это написано в таблице явно. Подготовить чек-лист из раздела 6.

Результат в документе: перечень эпиков и заполненный чек-лист.

#### Шаг 2. Проверка на полноту

Для каждой истории проверить четыре ответа: кто пользователь (роль), что он хочет сделать (действие), зачем (ценность), при каком условии это происходит (контекст). Отметить требования без роли, действия или ценности и написать, чем их дополнить.

| User Story | Роль | Действие | Ценность | Полнота |
|------------|------|----------|----------|---------|
| US-1: Как менеджер, я хочу видеть активные заявки, чтобы оперативно реагировать | ✓ | ✓ | ✓ | Полное |
| US-2: Система должна обрабатывать заявки | ✗ | ✓ | ✗ | Неполное |

Результат: список неполных требований с рекомендацией, чего не хватает.

#### Шаг 3. Проверка на однозначность и проверяемость

Найти размытые слова: «быстро», «удобно», «надёжно», «эффективно», «оперативно». Заменить их на наблюдаемый результат. Метрика берётся из материалов кейса или помечается как допущение со ссылкой на риск в документе концепции. Число «из головы» без такой пометки не ставится.

| Исходное требование | Проблема | Исправленное требование |
|---------------------|----------|-------------------------|
| «Система должна работать быстро» | Неизмеримо | «Система должна загружать список заявок за ≤ 2 секунды» |
| «Интерфейс должен быть удобным» | Неоднозначно | «Создание заявки должно занимать ≤ 3 клика» |
| «Система должна быть надёжной» | Непроверяемо | «Доступность системы ≥ 99.5% в месяц» |

Результат: таблица «проблемное требование → исправленное требование». Если размытых слов нет, в таблице одна строка «не выявлено» с перечислением эпиков, которые просмотрены.

#### Шаг 4. Проверка на непротиворечивость

Сравнить эпики попарно там, где они делят одну роль, одни данные или один режим работы. Конфликт не оставлять «на потом».

| Требование A | Требование B | Конфликт | Решение |
|--------------|--------------|----------|---------|
| US-1: Менеджер видит все заявки | US-5: Оператор видит только свои заявки | Конфликт прав доступа | Уточнить роли и разграничить доступ |
| US-2: Система работает офлайн | US-6: Система синхронизирует данные в реальном времени | Конфликт режимов работы | Уточнить сценарии использования |

Результат: список конфликтов с решением. Решение вносится в формулировку эпика или в сценарий, а не только в эту таблицу.

#### Шаг 5. Проверка на атомарность

Найти требования, в которых несколько самостоятельных целей связаны через «и», «или», «а также». Разделить их на отдельные эпики. Не дробить эпик до одного поля экранной формы: отдельное поле остаётся шагом сценария.

| Исходное требование | Проблема | Исправленные требования |
|---------------------|----------|-------------------------|
| US-3: Система должна создавать, редактировать и удалять заявки | Содержит 3 функции | US-3.1: создавать заявки; US-3.2: редактировать заявки; US-3.3: удалять заявки |

Результат: список после декомпозиции. Новые эпики получают собственные истории, сценарии и строки в остальных таблицах. Старый составной идентификатор в протоколе помечен как разделённый.

#### Шаг 6. Проверка на трассируемость

У каждого эпика есть уникальный идентификатор, источник (стейкхолдер) и связь с бизнес-целью документа концепции. В матрице та же цель, что уже записана в `case_concept.md` или в `RTM.md`. Новая цель, которой нет в концепции, в матрицу не добавляется: сначала она согласуется как изменение концепции.

| ID | Требование | Источник | Бизнес-цель | Связанные ФТ | Статус |
|----|------------|----------|-------------|--------------|--------|
| US-1 | Менеджер видит активные заявки | Менеджер | Сокращение времени реакции | ФТ-1.1, ФТ-1.2 | Проверено |
| US-2 | Оператор создаёт заявку | Оператор | Ускорение оформления | ФТ-2.1, ФТ-2.2 | Проверено |

В этой лабораторной колонка «Связанные ФТ» — узел скорректированного дерева функций и идентификатор варианта использования.

Результат: матрица трассировки без пустых источника и бизнес-цели.

#### Шаг 7. Проверка на приоритезированность

Каждому эпику назначен приоритет MoSCoW. Обоснование говорит, что ломается в кейсе без этого эпика, а не «это важно».

| ID | Требование | Приоритет | Обоснование |
|----|------------|-----------|-------------|
| US-1 | Менеджер видит активные заявки | Must have | Без этого невозможна работа отдела |
| US-3 | Руководитель получает отчёты | Should have | Важно для контроля, но можно отложить |

Результат: таблица приоритетов на все эпики, включая появившиеся при декомпозиции.

#### Шаг 8. Проверка с участием стейкхолдеров

Провести ревью набора с тем, кто играет заказчика, и с ролями пользователей кейса. Порядок ревью: представление эпиков, проход по диаграмме и одному-двум сценариям, вопросы, фиксация замечаний, правка документа.

Результат: протокол ревью. У каждого замечания есть автор, решение (принято или отклонено) и ссылка на изменённый эпик. Отклонённое замечание сопровождается причиной.

#### Шаг 9. Разбор с помощью ИИ

Прогнать перечень эпиков через одну языковую модель, доступную команде (GigaChat, YandexGPT, SourceCraft AI или другую, которой команда реально пользуется). В документ входят текст промпта, ответ модели и таблица, какие замечания приняты.

Промпт можно взять за основу и подставить свой перечень:

```text
Проанализируй следующие пользовательские требования на предмет неоднозначности, противоречий и неполноты. Предложи исправленные формулировки: [список требований]
```

Дополнительно команда может прогнать тот же текст библиотекой обработки языка (spaCy, NLTK, Transformers) и приложить, какие формулировки библиотека пометила. Этот прогон не заменяет таблицу принятых и отклонённых замечаний модели.

Результат: отчёт разбора. Замечание модели, которое принято, уже внесено в эпик. Замечание, которое отклонено, остаётся в таблице с причиной.

#### Шаг 10. Фиксация результатов

Составить протокол дефектов и обновить перечень требований. В конце документа — актуальные формулировки. История дефекта остаётся в протоколе, а не затирается.

| ID | Дефект | Тип дефекта | Рекомендация | Статус |
|----|--------|-------------|--------------|--------|
| US-2 | Отсутствует роль пользователя | Неполнота | Добавить роль | Исправлено |
| US-3 | Содержит 3 функции | Нарушение атомарности | Разделить на 3 требования | Исправлено |

## Типичные дефекты

| Дефект | Пример | Способ устранения |
|--------|--------|-------------------|
| Неполнота | «Система должна обрабатывать заявки» | Добавить роли, статусы, условия |
| Неоднозначность | «Система должна работать быстро» | Заменить на метрику |
| Непроверяемость | «Интерфейс должен быть удобным» | Задать измеримый критерий |
| Противоречивость | Конфликт прав доступа | Уточнить роли и разграничить |
| Нарушение атомарности | «Создавать и удалять заявки» | Разделить на два требования |
| Отсутствие трассируемости | Нет ID и источника | Присвоить ID и указать источник |
| Сущность без сценария | На схеме таблица, которой нет в эпиках | Оставить только то, что различает пользователь, остальное объяснить как атрибут или «вне рамок» |
| Отсутствие приоритета | Требование без MoSCoW | Присвоить приоритет |
| Нереализуемость | «Предсказывать будущее» | Переформулировать |
| Устаревшее требование | Функция, потерявшая актуальность | Удалить или отложить |

## Результаты сдачи

Работа сдаётся в том же репозитории, что и лабораторная работа 1. Файл без связи с деревом функций концепции не принимается.

| Результат | Где лежит |
|-----------|-----------|
| `Документ пользовательских требований.md` | Папка варианта, рядом с `case_concept.md` |
| Диаграмма прецедентов | `diagrams/usecase.puml` и тот же фрагмент в документе |
| Логическая схема данных | `diagrams/logical-data.puml` и тот же фрагмент в документе |
| Заполненный чек-лист, матрица трассировки, протокол ревью и протокол дефектов | Разделы этого же документа |
| Краткое упоминание нового файла | Студенческий `README.md` репозитория |

Обязательные разделы документа:

1. Исходное и скорректированное дерево функций, таблица сверки с эпиками.
2. Диаграмма вариантов использования и таблица «узел дерева → вариант использования → актор».
3. Эпики: у каждого история и сценарий.
4. Анализ сущностей и логическая схема данных со связями и кратностью.
5. Десять шагов проверки со своими таблицами, а не с текстом задания.
6. Чек-лист по каждому эпику.
7. Актуальный перечень после исправлений.

## Критерии оценивания

| Критерий | Баллы |
|----------|-------|
| Полнота проверки по всем критериям качества | 25 |
| Корректность выявления дефектов | 20 |
| Обоснованность рекомендаций по исправлению | 20 |
| Качество протокола проверки | 15 |
| Применение AI-инструментов | 10 |
| Оформление результатов | 10 |
| **Итого** | **100** |

Баллы за полноту проверки не ставятся, если в документе нет исходного дерева, сверки с эпиками, диаграммы прецедентов или логической схемы данных. Баллы за инструменты ИИ не ставятся, если в документе нет промпта и решения по замечаниям модели.
