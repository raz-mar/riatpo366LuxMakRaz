# Лабораторная работа 4

**Системная инженерия нефункциональных требований к управлению данными и информационной безопасности в кейсе индустриального партнёра: аутентификация, авторизация, структуры хранения и политики защиты, требования к развёртыванию, эксплуатации и межсервисному взаимодействию распределённого решения: протоколы, потоки данных и балансировка нагрузки**

Продолжение того же варианта. К функциям лабораторной работы 3 добавляются измеримые нефункциональные требования: защита и хранение данных, аутентификация и авторизация, развёртывание, эксплуатация, протоколы, потоки данных и балансировка нагрузки. Матрица трассировки закрывается целиком.

> [!NOTE]
> Новый кейс не выбирается. Берутся документ концепции, документ пользовательских требований и `Документ функциональных требований.md`. Итог — `Документ нефункциональных требований.md` в папке того же варианта. Заготовка: [`templates/Документ нефункциональных требований.md`](templates/Документ%20нефункциональных%20требований.md). Пример на справке: [`example/Документ нефункциональных требований.md`](example/Документ%20нефункциональных%20требований.md).

Тема 5. 4 часа.

Целевые компетенции блока декомпозиции: ППК-У1.1.У-1, ППК-У1.1.У-2, ППК-Р5.1.У-1, ППК-Р5.1.У-2, ППК-Р5.2.У-2, ППК-Р5.2.У-4, ППК-Р5.4.У-1, ИП-ДРБ-1.1.У-1, АР-2.1.У-3. В этой работе проверяются нефункциональные требования, их связь с функциями и завершённая матрица трассировки.

## Что необходимо

- Функции, оценки и матрица лабораторной работы 3.
- Материалы кейса из лабораторной работы 1: ограничения, регламенты, описания API и ландшафта, если они есть в папке варианта.
- Тот же репозиторий.
- Контур систем, если в кейсе есть смежные вызовы, — исходник PlantUML `diagrams/landscape.puml`. Картинка без кода не принимается.
- Контракт на каждый такой вызов и исходник последовательности `diagrams/sequence-<имя>.puml`. Заготовка последовательности: [`templates/diagrams/sequence.puml`](templates/diagrams/sequence.puml).

## Цель работы

Зафиксировать, как система обязана работать, а не только что она делает. Каждое такое требование измеримо, привязано к функции или к системе целиком и имеет критерий приёмки, по которому тестировщик понимает, что проверка пройдена.

## Вариант

Команда продолжает свой вариант. Нефункциональное требование описывает этот кейс. Числа из образца про заявки в документ кейса не переносятся. Метрика либо следует из материалов варианта, либо помечена как допущение со ссылкой на риск в документе концепции.

## Описание задания

### 1. Выделение нефункциональных требований

Для каждой функции и для системы в целом выделить характеристики качества по ISO/IEC 25010: эффективность производительности, совместимость, удобство использования, надёжность, защищённость, сопровождаемость, переносимость. Формулировка «Система должна…» сопровождается метрикой и условиями измерения.

Идентификатор — `НФТ-n`.

Образец приёма, не содержание кейса:

| Категория | Требование | Метрика |
|-----------|------------|---------|
| Производительность | НФТ-1: Система должна загружать список заявок за приемлемое время | Время отклика ≤ 2 сек при 100 одновременных пользователях |
| Масштабируемость | НФТ-2: Система должна поддерживать рост числа пользователей | Горизонтальное масштабирование до 1000 одновременных сессий |
| Безопасность | НФТ-3: Система должна обеспечивать защиту данных | Шифрование TLS 1.3, хеширование паролей bcrypt |
| Доступность | НФТ-4: Система должна быть доступна | Uptime ≥ 99.5% |
| Удобство | НФТ-5: Интерфейс должен быть интуитивным | Создание заявки ≤ 3 клика |
| Сопровождаемость | НФТ-6: Код должен быть документирован | Покрытие документацией ≥ 80% |

«Приемлемое время», «надёжно» и «интуитивно» без метрики в документ кейса не проходят. В образце они оставлены только в колонке требования, чтобы было видно, что именно заменяет метрика.

По названию работы в документе обязаны появиться требования девяти групп. Если группа кейсу не нужна, строка всё равно есть: «вне рамок» и ссылка на границы документа концепции.

| Группа | Что должно быть видно в требовании |
|--------|-------------------------------------|
| Аутентификация | Кто и чем подтверждает, что он тот, за кого себя выдаёт |
| Авторизация | Какая роль что может делать с данными кейса |
| Структуры хранения | Какие данные система хранит сама и какой смысл у этой группы для функций |
| Политики защиты | Что запрещено делать с данными помимо входа в систему |
| Развёртывание | Куда ставится система и от чего зависит запуск |
| Эксплуатация | Как понимают, что система жива, и кто об этом узнаёт |
| Протоколы | Чем система говорит со смежными системами варианта |
| Потоки данных | Какие сообщения или партии данных идут между частями решения |
| Балансировка нагрузки | Как делится нагрузка, если в кейсе больше одного экземпляра службы |

Смежную систему, которой нет в материалах варианта и в документе концепции, в протокол не добавляют.

### 2. Матрица трассировки

Дополняется матрица лабораторной работы 3. У каждой истории появляются связанные `НФТ`. У каждого `НФТ` есть источник: стейкхолдер, регламент или ограничение из концепции. Требование без источника не считается выявленным.

| ID | Тип | Источник | Связанные ФТ | Связанные НФТ | Приоритет | Критерий приёмки |
|----|-----|----------|--------------|---------------|-----------|------------------|
| US-1 | Пользовательское | Менеджер | ФТ-1.1, ФТ-1.2, ФТ-1.3 | НФТ-1, НФТ-5 | Must | Список заявок отображается ≤ 2 сек |
| US-2 | Пользовательское | Оператор | ФТ-2.1, ФТ-2.2, ФТ-2.3 | НФТ-3, НФТ-5 | Must | Заявка создаётся ≤ 3 клика |
| US-3 | Пользовательское | Руководитель | ФТ-3.1, ФТ-3.2 | НФТ-1 | Should | Отчёт формируется ≤ 5 сек |

Приоритет в этой таблице — приоритет истории. Приоритет самого `НФТ` задаётся отдельной таблицей: одно ограничение может быть Must, даже если связано с функцией Could, если без него нельзя вводить систему в эксплуатацию.

### 3. Приоритет нефункциональных требований

MoSCoW для каждого `НФТ`. Must означает, что выпуск нельзя принимать без этой метрики. Should можно отложить на следующий выпуск, если это явно сказано и функция без него всё ещё безопасна для кейса. Could не блокирует приёмку. Won't в этот выпуск не входит.

Модель Кано или сравнение стоимости и риска подключаются в той же ситуации, что в лабораторной работе 3: два требования спорят за один выпуск, и одного MoSCoW недостаточно.

### 4. Критерии приёмки

У каждого `НФТ` один сценарий Given–When–Then. В Then стоит та же метрика, что в таблице требования, а не новый порог.

Образец для скорости списка:

```text
Given: менеджер авторизован в системе
When: менеджер открывает раздел «Активные заявки»
Then: список заявок отображается в течение 2 секунд с возможностью фильтрации и сортировки
```

Для аутентификации, авторизации, хранения и протокола Then описывает наблюдаемый результат: отказ без права, запись в нужном хранилище, ответ смежной системы. «Система безопасна» в Then не пишется.

### 5. Две оценки на каждое нефункциональное требование

Функциональные точки заново по нефункциональному требованию не считаются: точками измерен объём функций в лабораторной работе 3. У каждого `НФТ` в строке два числа.

1. Объём связанных функций в функциональных точках. Берётся сумма точек тех `ФТ`, на которые требование влияет. Одно и то же ограничение на всю систему ссылается на сумму точек затронутых функций, а не на повторный подсчёт файлов.
2. Пользовательские поинты на реализацию самого ограничения. Раунд покера тот же, что в лабораторной работе 3: карты 1, 2, 3, 5, 8, 13, 21, одновременный ход, объяснение крайних карт, итог. Оценивается работа, чтобы метрика стала истинной, а не размер хранимых данных.

Пример чтения строки, не для копирования. НФТ «список заявок за ≤ 2 секунды» связан с ФТ-1.1 на 3 функциональные точки. Реализация кэша и замера может стоить 8 пользовательских поинтов. Оба числа стоят в строке. Из них не вычитают и не делают третье «среднее».

### 6. Контракты взаимодействия

На каждый смежный вызов из контура систем — один контракт. Смежную систему, которой нет в материалах варианта и в документе концепции, в контракт не добавляют. Если группы «протоколы» и «потоки данных» закрыты пометкой «вне рамок», контрактов нет: одна фраза и ссылка на границы концепции.

Идентификатор — `КНТ-n`.

Контракт читается как требование к границе и как описание сообщения. В нём видно:

- формулировку «система должна»: какой результат вызывающая сторона обязана получить этим вызовом;
- стороны: кто поставщик, кто потребитель;
- протокол: SOAP, REST или gRPC — тот, которым эта система говорит;
- имя операции, предусловие, постусловие успеха и постусловие отказа;
- таблицу полей запроса и ответа: имя, место в сообщении, тип, обязательность, смысл в кейсе, правило;
- пример сообщения в формате выбранного протокола;
- таблицу исходов: что пришло, что это значит в кейсе, что делает вызывающая сторона. Отказ не записывается как успешный результат соседней ветки;
- приёмку Given–When–Then на успех и на исход, который легко спутать с успехом.

Формат записи совпадает с протоколом. Ниже образец приёма, не содержание кейса. Пути, имена операций и значения полей в документ варианта не переносятся.

REST, чтение:

```http
GET /orders/{id}

200 { "id": "A-14", "status": "open" }
```

Нет ответа — вызывающая сторона не подставляет `"status": "closed"`.

SOAP, та же обязанность другим конвертом:

```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <GetOrderStatus>
      <orderId>A-14</orderId>
    </GetOrderStatus>
  </soap:Body>
</soap:Envelope>
```

Ответ — статус заказа или `soap:Fault`. Fault не читается как успешный статус.

gRPC, один запрос и один ответ. Поток сообщений в этот образец не входит:

```protobuf
service Orders {
  rpc GetOrder (OrderRequest) returns (OrderReply);
}

message OrderRequest { string order_id = 1; }
message OrderReply { string order_id = 1; string status = 2; }
```

Код недоступности сервиса не заменяется ответом со статусом `closed`.

Рядом с контрактом — диаграмма последовательности в PlantUML: порядок сообщений и ветка ошибки. Исходник `diagrams/sequence-<имя>.puml`. Картинка без кода не принимается. Заготовка: [`templates/diagrams/sequence.puml`](templates/diagrams/sequence.puml).

В примере справки три вызова и три последовательности: [`sequence-status.puml`](example/diagrams/sequence-status.puml) (REST), [`sequence-sign.puml`](example/diagrams/sequence-sign.puml) (SOAP), [`sequence-journal.puml`](example/diagrams/sequence-journal.puml) (gRPC). Три протокола у одной справки — допущение примера. В кейсе с одним REST пишется один контракт REST. Остальные форматы ради сходства с примером не выдумывают.

| Критерий | Баллы |
|----------|-------|
| Полнота нефункциональных требований, включая группы из названия работы и контракт на каждый смежный вызов | 25 |
| Измеримость требований | 25 |
| Корректность матрицы трассировки | 20 |
| Обоснованность приоритезации | 10 |
| Качество критериев приёмки | 10 |
| Оформление отчёта | 10 |
| **Итого** | **100** |

Баллы за измеримость не ставятся, если в Then другая цифра, чем в метрике требования. Баллы за матрицу не ставятся, если `НФТ` не связан ни с функцией лабораторной работы 3, ни с явным ограничением на всю систему. Баллы за полноту не ставятся, если смежный вызов из контура описан без протокола, состава сообщения и ошибки. Баллы за оформление не ставятся, если последовательность вызова приведена картинкой без исходника PlantUML.
