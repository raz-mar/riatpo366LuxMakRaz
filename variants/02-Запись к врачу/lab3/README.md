## Цель работы

Получить по каждой пользовательской истории набор наблюдаемых функций и понять объём их реализации до того, как появятся задачи разработки. Функция без истории-источника в документ не входит. История без хотя бы одной функции считается не разложенной.

## Вариант

Команда продолжает свой вариант. В работу входят истории, которые после проверки лабораторной работы 2 остались в актуальном перечне. История со статусом «отложена» или «вне рамок» в функции не раскладывается: в таблице декомпозиции стоит пометка и ссылка на протокол лабораторной работы 2.

## Описание задания

Таблицы про заявки сервисного центра ниже — образец приёма. В сдаваемый документ попадают функции вашего кейса.

### 1. Декомпозиция историй в функциональные требования

Для каждой актуальной пользовательской истории определить функции, без которых история не выполняется. Каждую функцию записать формулой «Система должна…» и дать идентификатор `ФТ-n.m`: `n` — номер истории, `m` — номер функции внутри неё.

Функция описывает поведение системы, а не намерение пользователя. «Менеджер хочет видеть заявки» остаётся историей. «Система должна отображать список активных заявок» — функция.

| User Story | Функциональные требования |
|------------|---------------------------|
| US-1: Менеджер видит активные заявки | ФТ-1.1: Система должна отображать список активных заявок. ФТ-1.2: Система должна поддерживать фильтрацию по статусу заявки. ФТ-1.3: Система должна поддерживать сортировку по дате создания. |
| US-2: Оператор создаёт заявку | ФТ-2.1: Система должна предоставлять форму создания заявки. ФТ-2.2: Система должна валидировать обязательные поля. ФТ-2.3: Система должна сохранять заявку в базе данных. |
| US-3: Руководитель получает отчёты | ФТ-3.1: Система должна формировать отчёт по количеству обработанных заявок. ФТ-3.2: Система должна поддерживать экспорт отчёта в формате Excel. |

Результат: таблица «история → функциональные требования» по всем актуальным историям кейса.

### 2. Спецификация и визуализация

У каждой функции в документе есть идентификатор, формулировка «Система должна…», история-источник, актор, входные данные, результат и что система делает при ошибочном входе.

Поведение функции задаётся сценарием приёмки Given–When–Then. Один сценарий — одна функция. Общий сценарий на всю историю не заменяет сценарии функций.

Пример для ФТ-2.1:

```text
Given: оператор авторизован в системе
When: оператор заполняет обязательные поля и нажимает «Сохранить»
Then: заявка сохраняется и отображается в списке активных заявок
```

Схема декомпозиции показывает те же идентификаторы, что таблица: история, под ней функции. Исходник — `diagrams/decomposition.puml` в репозитории, в документе — тот же код или ссылка на файл. Функция, которая есть в таблице и отсутствует на схеме, считается не визуализированной.

### 3. Приоритет функций

Каждой функции назначается приоритет MoSCoW. Он не копируется с истории автоматически: внутри одной истории одна функция может быть Must, другая — Could. Обоснование говорит, выполняется ли история без этой функции.

| Приоритет | Смысл в этой работе |
|-----------|---------------------|
| Must have | Без функции история не выполняется |
| Should have | История выполняется урезанно, функцию нельзя откладывать дольше ближайшего следующего выпуска |
| Could have | Функцию можно снять с ближайшего выпуска без потери истории |
| Won't have | Функция осознанно не входит в этот выпуск |

Модель Кано или сравнение стоимости и риска нужны только там, где одного MoSCoW мало, чтобы выбрать между двумя Should. Тогда в обосновании одна фраза, почему выбран этот приоритет.

### 4. Две оценки сложности на каждую функцию

У каждой `ФТ` в одной строке стоят оба числа: функциональные точки и пользовательские поинты. Одно число вместо двух не принимается. Поинты не переводятся в часы и не подменяются функциональными точками.

#### Функциональные точки

Считается нескорректированный объём по упрощённой схеме IFPUG. Общие характеристики системы и коэффициент поправки в эту лабораторную не входят: их место в нефункциональных требованиях работы 4.

Тип элемента:

| Тип | Что это для функции |
|-----|---------------------|
| EI, внешний вход | Система принимает данные и меняет внутреннее хранилище |
| EO, внешний выход | Система отдаёт данные и при этом что-то вычисляет |
| EQ, внешний запрос | Система отдаёт данные без вычисления и без смены хранилища |
| ILF, внутренний логический файл | Группа данных, которую система сама хранит |
| EIF, внешний интерфейсный файл | Группа данных, которую система читает из чужого хранилища |

Вес по сложности, учебная таблица IFPUG:

| Тип | Низкая | Средняя | Высокая |
|-----|--------|---------|---------|
| EI | 3 | 4 | 6 |
| EO | 4 | 5 | 7 |
| EQ | 3 | 4 | 6 |
| ILF | 7 | 10 | 15 |
| EIF | 5 | 7 | 10 |

Сложность выбирается по числу полей и числу связанных групп данных и коротко объясняется. «Высокая, потому что сложно» объяснением не считается.

Референс метода — разбор ФТ-1.3 в примере на справке: элементарный процесс, выбор типа, формулы DET и FTR, матрицы сложности, вес и то, какие точки группы данных к функции не прибавляются. Считать свой кейс нужно теми же шагами. Числа справки в вариант не переносятся.

[Расчёт функциональных точек на ФТ-1.3](example/Документ%20функциональных%20требований.md#ft-1-3-fp)

Учебный фрагмент про заявки, не про ваш кейс и не вместо референса. Список активных заявок — запрос без расчёта, мало полей, одна группа данных: EQ, низкая сложность, 3 точки. Фильтр по статусу входит в тот же запрос, отдельную точку не получает. Сохранение заявки — вход, мало полей: EI, низкая, 3 точки. Отчёт с итогом по заявкам — выход с расчётом: EO, средняя, 5 точек. Хранимая заявка — внутренний файл, одна группа, мало полей: ILF, низкая, 7 точек. Сумма фрагмента: 3 + 3 + 5 + 7 = 18 функциональных точек. В документе кейса так же виден тип, сложность, вес и сумма по всем функциям. Полные формулы этого фрагмента не повторяют: они записаны в разборе ФТ-1.3.

Один внутренний файл не считают заново на каждую функцию, которая его трогает. Файл оценивается один раз и указывается у функций, которые его читают или меняют.

#### Пользовательские поинты, покер планирования

Относительная трудоёмкость для команды, шкала 1, 2, 3, 5, 8, 13, 21. Это не часы и не функциональные точки.

Порядок раунда:

1. Функция зачитывается целиком, вместе со сценарием приёмки.
2. Участники задают вопросы только о смысле функции.
3. Каждый одновременно называет карту. Роли те же, что в проверке лабораторной работы 2: аналитик, разработчик, тестировщик. Если человека на роль нет, это написано в протоколе раунда.
4. Крайние карты объясняются. После этого раунд повторяется.
5. В документ попадают карты, итог и одна фраза, что именно раздувает оценку.

Учебный итог того же фрагмента, не норматив для кейса: ФТ-1.1 — 3 поинта, ФТ-1.2 — 2, ФТ-1.3 — 2, ФТ-2.1 — 5, ФТ-2.2 — 3, ФТ-2.3 — 5, ФТ-3.1 — 8, ФТ-3.2 — 5. Расхождение с функциональными точками нормально: отчёт может быть небольшим по данным и дорогим по правилам расчёта.
